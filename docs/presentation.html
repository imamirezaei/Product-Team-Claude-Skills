Context

What we observed

Pain point 1

Decisions disappear

Important product decisions — UX choices, scope trade-offs, rejected ideas — get made in meetings and Slack but never written down. Six months later, nobody knows why something was built a certain way.

Pain point 2

Silent scope trade-offs

When a manager adds a new request, PMs accept it by quietly dropping something else from the roadmap. The trade-off is never explicit and never visible to the team.

Pain point 3

Requirements miss edge cases

PMs define the happy path well. But edge cases — what happens when a payment is pending, when a user has no permissions, when a service is down — get discovered by engineering mid-implementation.

Pain point 4

No awareness of technical cost

PMs can't easily see what a feature touches in the codebase. They don't know which modules are affected, which shared services are involved, or what might break when something changes.

Design principle

One system, two separations

The system separates what is fixed from what is personal — and separates Claude's instructions from Claude's knowledge of the product.

Policy Layer — fixed for all PMs
rules · commands · output format · skill logic
Supervisor defines · git pull to update
↕
Interview Engine — run once per PM
structured interview → 13 personalized files
One session · generates everything
↕
Dynamic Layer — unique per PM
CLAUDE.md · 11 context files · product agent
Output of interview · committed to repo
↕
Personal Layer — private
CLAUDE.local.md · settings.local.json
PM only · gitignored · never shared

The key insight: When the supervisor updates a skill or rule, only the Policy Layer changes. Each PM's CLAUDE.md and context files stay untouched. No merge conflicts. No re-interview.

Layer 1 · Policy

6 hard rules

Rules are enforced at the Policy Layer and cannot be overridden by any PM. They define what Claude is and is not allowed to do in this workflow.

No technical decisions
Claude never picks an architecture, data model, or implementation approach. It identifies that a technical decision is needed, explains what is at stake, and flags who should make it.
no-technical-decisions.md
No scope expansion
Claude never adds features or requirements beyond what the PM explicitly described. If something seems like an obvious gap, it notes it once at the end — never in the deliverable.
no-scope-expansion.md
Persian output by default
All output in Persian. Technical terms, module names, API names, and tool names stay in English. Mixed language is the correct and expected format.
persian-output.md
Flag authority limits
Any recommendation that is outside the PM's defined authority boundary must be marked ⚠️ with an explicit note about who needs to sign off. Claude never suggests unilateral action on things that require approval.
flag-authority-limits.md
Always include DOD
Every feature-related output must include a DOD. If the PM hasn't defined one, Claude generates a draft and asks for validation. A deliverable without a DOD is rejected.
always-include-dod.md
Always include edge cases
No requirement document is accepted without edge case coverage. Happy-path-only specs are incomplete by definition. If edge cases are unknown, they are flagged as open questions — never silently ignored.
always-include-edge-cases.md
Process

PM onboarding — 7 steps, done once

From zero to a fully personalized Claude Code setup. Steps 1–2 take minutes. Step 3 is the interview — the only substantial time investment.

1

Clone the workflow repo inside the product repo

One git command. The workflow repo lives as a subfolder and never interferes with product code.

git clone https://github.com/imamirezaei/Product-Team-Claude-Skills.git claude-workflow
2

Copy the pm-template to repo root

Copies the CLAUDE.md placeholder, .claude/ directory structure, and .gitignore.

cp claude-workflow/pm-template/CLAUDE.md ./CLAUDE.md
cp -r claude-workflow/pm-template/.claude ./.claude
cp claude-workflow/pm-template/.gitignore ./.gitignore
3

Run the interview

Open interview/pm-interview.md, paste it into Claude, answer the questions. Claude generates 13 files at the end.

4

Place the 13 output files in the correct paths

CLAUDE.md in root. 11 context.md files in their skill directories. product-agent.md in agents/. The README table maps every file to its destination path.

5

Commit and push

git add CLAUDE.md .claude/ .gitignore && git commit -m "feat: add Claude PM workflow context" && git push
6

Send output to supervisor for review

Supervisor reviews the generated CLAUDE.md and context files before the PM starts using the workflow in production.

7

Start working

Open Claude Code at repo root. Use slash commands or call skills directly.

/new-feature add biometric authentication to checkout flow
Process

Receiving updates — one command

The separation of Policy Layer and Dynamic Layer means supervisor updates never touch PM-owned files. No merge conflicts.

When supervisor updates a skill or rule

Supervisor pushes to product-team-claude-skills repo. PM runs:

cd claude-workflow && git pull && cd ..

That is the entire update process. Nothing else required.

Summary

What this system delivers

Consistency without uniformity

Every PM follows the same rules and output format. But each PM's Claude understands a different product, team, and set of constraints. Policy is shared. Context is personal.

Supervisor control at scale

One push to the workflow repo propagates to all PMs. Skill logic, rules, and commands are versioned and auditable. No PM can override policy-layer constraints.

Technical awareness without technical debt

Skills that read the codebase (feature-dependency, design-system-check, release-impact, qa-guide) give PMs accurate technical context without requiring them to understand the code.
