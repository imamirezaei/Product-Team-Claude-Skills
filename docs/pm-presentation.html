Why generic AI tools fall short for PMs

Every request to a generic assistant starts from zero — no product context, no team knowledge, no PM-specific behavior.

Pain point 1

No product context

Claude doesn't know your stack, your team structure, or your decision boundaries. Every session starts blank.

Pain point 2

Generic output format

Responses aren't structured for PM deliverables. No DOD, no out-of-scope section, no authority flags.

Pain point 3

No skill specialization

A spec request, an edge-case analysis, and a feature prioritization are all treated the same way.

Pain point 4

Technical overreach

Generic Claude recommends architecture and tech stack choices — decisions that belong to engineering, not PM.

Design Principle

4-Layer Context Assembly

Every Claude response is built from four layers merged at request time. The policy layer is fixed and shared. The dynamic layer is unique to each PM and product.

Request Assembly

How a Claude request is formed

When you run a command, Claude assembles context from all four layers before generating a single word of output. Here's exactly what happens for /new-feature payment gateway.

1

CLAUDE.md is loaded automatically

Claude Code always injects CLAUDE.md into the system prompt. It contains your PM profile, product name, team structure, decision authority boundaries, and working language.

2

Command file is read

~/.claude/commands/product-manager/new-feature.md defines the chain: problem-framing → feature-dependency → edge-case-finder → design-system-check → wireframe-generator → feature-spec. Claude runs each in order.

3

SKILL.md is read for each skill

~/.claude/skills/product-manager/problem-framing/SKILL.md defines what the skill does and how — instructions, output format, edge case dimensions, and DOD requirements. This is the fixed policy.

4

context.md is read for the same skill

.claude/skills/product-manager/problem-framing/context.md contains who and what — your product domain, user types, typical constraints, and known edge cases. This was written by the interview engine.

5

Layers are merged into a complete context

SKILL.md (instructions) + context.md (product knowledge) + CLAUDE.md (PM profile) + output-style = a fully contextualized, PM-specific request. No context needs to be re-explained in the chat.

SKILL.md answers "how". context.md answers "for what product and team". Together they replace the paragraphs of context you'd otherwise type every time.

Layer 1 · Policy

6 hard rules — always active

Rules are enforced in every response, regardless of which skill or command is running. They cannot be overridden by the PM in the chat.

no-technical-decisions PM only
Claude flags technical decisions but never makes them. Always includes a 📖 Further Reading block so the PM can prepare for the engineering conversation.
no-scope-expansion PM only
Claude never adds features or requirements the PM didn't ask for. At most one out-of-scope note per skill if something critical is missing.
always-include-dod PM only
Every feature-related output includes a Definition of Done. The DOD is not optional — it is required for the output to be considered complete.
always-include-edge-cases PM only
No requirement passes without edge case coverage. Every requirement output includes at minimum a risk-flagged edge case list.
flag-authority-limits Shared
Any decision outside the PM's authority is marked ⚠️ Needs Approval with a clear statement of who must approve and why.
working-language Shared
All outputs are in the PM's chosen language (Persian or English). Technical terms stay in English regardless. Set once in CLAUDE.md, never changed by Claude.
Process · Setup

Init flow — from zero to ready

Run claude-pm init --role pm from your product repo. The entire setup takes under a minute.

1

Guard checks

Verifies git repo exists. Checks for prior initialization (use --force to override). Warns if Claude Code is not detected.

2

Global install → ~/.claude/

Copies all 15 skill files, 9 commands, output style, and /start-interview command. Never overwrites existing files unless forced.

3

Project scaffold → product repo

Copies full policy/ tree to claude-workflow/policy/, writes placeholder CLAUDE.md, settings.json, product-agent.md, and 11 context.md placeholders. Creates .claude/outputs/.

4

Gitignore patch

Adds CLAUDE.local.md and .claude/settings.local.json to .gitignore. These files are never committed.

5

Run /start-interview in Claude Code

Opens the 647-line PM interview. Asks working language first. Generates 14 files. PM approves each write. Context persists forever — update only the files that change.
